Build it. Deploy it. Understand it.

A human-friendly, step-by-step guide to taking a website from your computer to the internet with Cloudflare. Learn the requirements, choose the right platform, deploy plain HTML/CSS/JavaScript or a framework, and prepare your project for real users.

01 / Before you begin

What are you building?

Do not add complicated tools just because they are popular. First decide what the website needs to do.

A · STATIC

Plain HTML, CSS and JavaScript

A portfolio, landing page, business website, documentation site or browser-only tool. These files can be published directly; no React, Node server or build step is required.

Learn the static deployment path ↓
B · FRAMEWORK

Vite or another framework

React, Vue, Svelte, Angular, Astro and similar tools often compile source code into a folder of static files. The build command and output folder must match the project.

Learn framework settings ↓
C · FULL STACK

Website plus backend

Login, protected APIs, webhooks, database access, scheduled tasks and server-rendered routes need server-side logic. Cloudflare Workers can run that logic.

Learn Workers ↓
What you need at minimum: a Cloudflare account, website files, and a browser. GitHub is recommended for version control and automatic deployments. A custom domain is optional for the first deploy. You do not need to rent a traditional server to publish a static site.

02 / Choose the right product

Cloudflare Pages or Workers?

Both can deliver websites. The right choice depends on the project and the kind of runtime it needs.

Cloudflare Pages

Useful for straightforward static websites, static framework output and existing Pages projects. Git integration can rebuild the site whenever you push changes. Pages Functions can add server-side endpoints to a Pages project.

  • Static HTML, CSS, JS and images
  • Frameworks that produce static output
  • Git-connected builds and preview URLs
  • Functions for supported server-side routes
Official Pages documentation ↗

Cloudflare Workers

Useful for APIs, request handling, server-side logic, and modern full-stack applications. Workers Static Assets can serve frontend files and combine them with Worker code.

  • Static assets plus dynamic routes
  • APIs and webhook handlers
  • Bindings to supported data/storage services
  • Broader Workers platform capabilities
Official Workers documentation ↗
Practical recommendation: for a small HTML/CSS/JS website, Pages is a simple starting point, and Workers Static Assets is another valid route. Cloudflare's current guidance recommends Workers for new projects needing broader platform capabilities. For an existing Pages project, there is no reason to migrate without a real need. Check the current docs before committing to framework-specific features.

03 / Deployment tutorial

Publish plain HTML, CSS and JavaScript

Follow these steps in order. This is the simplest path for a site made of files such as index.html, styles.css and script.js.

1

Prepare the project folder

Keep your homepage at the top of the folder you intend to publish. For example:

my-website/
├── index.html
├── about.html
├── css/
│   └── styles.css
├── js/
│   └── app.js
└── images/
    └── logo.png

Check that paths in your HTML match the real folders and filenames. Deployed environments are case-sensitive, so Logo.png and logo.png may be different files.

2

Test it locally

Open index.html in a browser for a basic check. If your project uses JavaScript modules or fetch requests, use a local development server. Test on mobile and desktop; click every link; inspect the browser console for errors.

A form that looks correct is not automatically functional. Static hosting alone does not process submissions. A working form needs a backend, form service or suitable API.

3

Push the project to GitHub

Create a repository on GitHub. In a terminal opened inside the project folder, run:

git init
git add .
git commit -m "Add website"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git
git push -u origin main

Replace the sample URL with your own repository. If the project already has Git configured, check git status and git remote -v first instead of reinitializing it. Never commit access tokens or passwords.

4

Create a Pages project

Sign in to Cloudflare and open Workers & Pages. Choose to create an application, select Pages, then connect to Git. Authorize access to the right GitHub account/repository, select the repository and production branch (commonly main).

5

Set the build options correctly

For plain static files that need no build:

  • Production branch: main (or the branch you actually use)
  • Build command: exit 0 is the documented no-build option
  • Build output directory: the directory containing the deployed files and top-level index.html

If the files are at the repository root, use the dashboard's root-directory option. If they live in a folder such as site, use that folder. Do not enter dist unless the files really are in dist.

6

Deploy and test the live URL

Start the deployment and wait for the successful status. Cloudflare gives the project a *.pages.dev URL. Open it on your phone and computer. Check the homepage, navigation, stylesheets, images, links, mobile layout and any forms. A green deployment status does not guarantee every feature works.

7

Make future updates safely

With Git integration enabled, pushes to the configured production branch trigger deployments. A safer workflow is to create a branch, make a change, preview it, and merge when it looks right. Check the deployment result after every production update.

04 / Dynamic websites

Workers and APIs, explained simply

Your browser code is public. A Worker can perform trusted server-side work without asking you to manage a traditional server.

When you need a Worker

  • An API endpoint for your frontend
  • A payment-provider webhook
  • Server-side use of a private API key
  • Authentication and access checks
  • Data processing or scheduled work
  • Dynamic responses alongside static assets

What to prepare

  • Cloudflare account and project permissions
  • JavaScript or TypeScript source code
  • Node.js/npm and Wrangler for common CLI workflows
  • Configuration for routes and asset directories
  • Database/storage resources if needed
  • Server-side secrets and access policies

A tiny Worker API example

This example returns a JSON health response. It is a learning example, not a complete production API.

export default {
  async fetch(request, env) {
    const url = new URL(request.url);

    if (url.pathname === "/api/health") {
      return Response.json({ status: "ok" });
    }

    return new Response("Not found", { status: 404 });
  }
};

The env argument provides configured bindings and secrets. The example does not use it yet. A real API may need authentication, authorization, input validation, rate limits, safe error handling and logging that avoids sensitive data.

Deploy static assets with Workers

For the CLI workflow, Cloudflare provides a project starter. One common starting command is:

npm create cloudflare@latest -- my-static-site

Follow the prompts and select a static-site or suitable full-stack starter. For an existing project, follow the current Workers Static Assets instructions and point the asset directory at the actual deployable files. Use npx wrangler dev to test locally and npx wrangler deploy when the project is configured and ready. Exact setup depends on the starter and its Wrangler configuration.

Never expose secrets: do not place private payment keys, privileged database credentials or private API tokens in HTML, frontend JavaScript, public Git history or browser-exposed environment variables. Store secrets using the platform's supported secret configuration and call the private service from server-side code.

Storage and data options

  • D1: managed SQL database.
  • KV: key-value storage for suitable lookup patterns.
  • R2: object/file storage.
  • Queues: asynchronous work processing.
  • Durable Objects: stateful coordination and suitable real-time workloads.
  • External database: an option when the provider and connection model suit the app.

These resources are not automatically created just because you deploy a Worker. Create the resource, configure its binding securely, and design access permissions and data handling.

05 / Frameworks

Which frameworks can you use?

Cloudflare supports many frameworks. What matters is whether your app produces static files or requires server-side rendering and framework-specific runtime support.

Frontend / build tools

Vite, React, Vue, Angular, Svelte and similar frontend stacks. React is a UI library, so check whether the project uses Vite, Next.js or another build system.

Content and static sites

Astro, Hugo, Jekyll, Eleventy, Docusaurus, VitePress and other static site generators.

Full-stack / server-rendered

Next.js, Nuxt, SvelteKit, Remix and other frameworks with server routes or SSR. Confirm the current Cloudflare adapter and feature support before deploying.

API frameworks

Hono and other supported JavaScript frameworks can be used for Worker request handlers and APIs.

Build settings in plain English

  • Build command: the command that transforms source files into deployable output, often npm run build.
  • Build output directory: the folder produced by the build. Vite commonly uses dist; other projects may use build, out or another folder. Check the actual project.
  • Root directory: the folder containing the app in a monorepo.
  • Environment variables: configuration for builds or runtime. If a variable is embedded in frontend code, assume visitors can see it.
  • Production branch: the Git branch whose deployment is treated as production, often main.
Next.js note: a static export is not the same as a full server-rendered Next.js app. Cloudflare has distinct guidance for static Pages exports and Next.js on Workers. Read the guide for the framework's version and features instead of copying settings from a different tutorial.

Framework deployment checklist

  1. Read the official guide for the framework and version.
  2. Decide if the app is static or server-rendered.
  3. Check package.json scripts and the lockfile.
  4. Run a clean install and build locally.
  5. Confirm the output folder exists and contains the expected files.
  6. Configure the matching preset, root, command and output folder.
  7. Configure server-side bindings and secrets only when needed.
  8. Test routes, API calls, redirects and error states on the preview.

06 / Go live

Domains, DNS, HTTPS and production checks

A successful first deployment is the start. Make sure people can find the right site, use it safely and recover when something breaks.

Connect a custom domain

  1. Own the domain or have permission from its owner.
  2. Open the relevant Pages project or Worker and find custom-domain settings.
  3. Add the exact hostname, such as www.example.com or example.com.
  4. Follow the DNS instructions shown for that project and wait for validation/certificate setup.
  5. Test HTTPS and decide which hostname should be canonical.

Do not delete DNS records just to make the website work. MX, SPF, DKIM and DMARC records may be needed for business email. DNS changes can affect services other than the website.

Security checklist

These checkboxes are a local checklist for your browser; they do not change Cloudflare settings. For payment or personal-data systems, use a proper security review and follow applicable laws and provider requirements.

Troubleshooting common errors

My site returns 404

For a static site, confirm there is a top-level index.html in the deployed output directory. For a framework, check that the configured output directory matches the folder the build actually created.

CSS or images do not load

Inspect browser developer tools → Network, check capitalization and path spelling, and confirm the files were committed and included in the deployed output. A leading slash points to the domain root.

The deployment build fails

Read the first useful error in the build log. Confirm the branch, root directory, build command, dependencies, environment variables and output directory. Do not use a framework build command for plain static files.

It works locally but not online

Check for hard-coded localhost URLs, missing production variables, CORS/authentication settings, unsupported runtime APIs, and browser console/network errors.

My form looks right but sends nothing

Static hosting does not process a form by itself. Connect a real backend endpoint or form service, validate input, handle success and failure, and protect any sensitive operation on the server.

My API returns 500

Review Worker or Function logs, verify binding names and database permissions, and add safe error handling. Do not print secret values or expose raw stack traces to users.

My domain or certificate is pending

Review the domain status and exact DNS validation instructions in Cloudflare. Avoid repeatedly changing records or deleting email records without understanding their purpose.

07 / Business email

Email routing, domain records and sending mail

Your website domain and your email service share DNS, but they are different services. Set up email deliberately so a website change does not break business email.

Understand the difference: Cloudflare Email Routing forwards incoming messages sent to custom addresses (for example, hello@yourdomain.com) to an existing inbox. It is not, by itself, a full mailbox hosting service with a separate inbox, folders, IMAP/POP access, or a complete outbound email system.

A. Before you configure routing

  1. Add your domain to Cloudflare and use Cloudflare as its authoritative DNS provider. Email Service routing requires Cloudflare DNS.
  2. Decide which addresses you need, such as hello@yourdomain.com, support@yourdomain.com, sales@yourdomain.com and billing@yourdomain.com.
  3. Choose an existing mailbox that will receive forwarded messages, and make sure you can open and verify it.
  4. Inspect existing DNS records first. If the domain already uses Google Workspace, Microsoft 365 or another email provider, do not replace its MX records blindly.

B. Configure Cloudflare Email Service / Email Routing

  1. Open the Cloudflare dashboard and go to Compute → Email Service → Email Routing (the dashboard label may change).
  2. Choose the domain and start onboarding. Review the DNS records Cloudflare proposes to add, including the MX and relevant authentication records.
  3. Open Destination Addresses, add the inbox where you want to receive forwarded messages, and click the verification link sent to that mailbox.
  4. Create a custom address and choose the verified destination. Repeat for other addresses if needed.
  5. Send a test message from an unrelated email account. Confirm delivery to the destination inbox and check spam/junk if it does not arrive.
  6. Review routing analytics and troubleshoot DNS or verification warnings shown by Cloudflare.

Official setup: Route emails with Cloudflare Email Service ↗ · Email Service documentation ↗

C. DNS records in simple terms

MX

Tells other mail systems where incoming mail for your domain should be delivered. Incorrect MX records can stop mail from reaching your current provider.

SPF, DKIM and DMARC

Help receiving mail systems evaluate whether messages are authorized and authenticated. Follow the exact records supplied by your email provider; do not copy records from a different domain.

A and CNAME

Typically connect a website hostname to a hosting destination. These records do not create an email inbox. Keep web and mail records distinct.

DNS propagation

Changes may take time to appear across the internet. Check the record values and status before making repeated edits.

D. Can I send email from my website?

Incoming forwarding and outbound email are separate. A contact form, password reset, receipt or booking confirmation needs a sending service or a supported email API. Cloudflare Email Service includes sending capabilities, but you must configure the domain and sending workflow according to its current documentation. A third-party provider is also an option.

  • Keep API keys and provider credentials in Worker secrets or your backend's secret manager, never in browser JavaScript.
  • Validate form input on the server and add rate limiting, abuse protection and sensible message limits.
  • Use a verified sender domain and correctly configured SPF/DKIM/DMARC as instructed by the provider.
  • Handle delivery failures gracefully and avoid exposing whether a private account exists in password-reset flows.
  • Test delivery to multiple providers and check spam placement, not just the success response from an API.
Important: Email routing is not an email marketing list, a mailbox, or a guarantee that outbound messages will be accepted. Before changing MX records on a domain that already receives mail, document the existing configuration and plan the migration.

08 / Operating the site

SEO, analytics, forms, performance and maintenance

A professional website needs more than a successful deploy. Make it discoverable, measurable, accessible and maintainable.

Search engine basics

  • Give each page a useful, unique title and meta description.
  • Use semantic headings, descriptive link text, image alt text and readable page content.
  • Add a valid robots.txt and sitemap when appropriate; submit the sitemap to search tools you use.
  • Use one preferred canonical hostname and redirect alternate versions consistently.
  • Do not hide important content in images or rely only on client-side scripts for essential information.

Analytics and privacy

Cloudflare Web Analytics can provide website traffic measurements. Enable it from the dashboard or follow the current setup guide, then check that the site is actually receiving data. Explain tracking honestly and follow privacy requirements applicable to your audience. Do not collect more personal information than you need.

Cloudflare Web Analytics guide ↗

Forms and integrations

HTML can display a contact form, but static hosting does not automatically store or deliver its submissions. Connect a secure Worker/Pages Function or a reputable form service. Validate fields on the server, protect against spam, show clear success and error states, and do not collect payment-card data yourself.

Speed and accessibility

  • Compress images and use suitable formats and dimensions.
  • Reduce unnecessary JavaScript and third-party scripts.
  • Check the page at narrow mobile widths, with keyboard navigation and zoom.
  • Maintain sufficient contrast, visible focus states, labels and meaningful alt text.
  • Use caching thoughtfully; do not aggressively cache private or personalized responses.

Backups, monitoring and rollbacks

Keep the source in Git, document DNS and environment settings, and maintain a recovery path. Review deployment logs after changes, test critical journeys and keep secrets out of logs. Pages supports deployment history and rollbacks; use the dashboard to return to a known-good deployment when appropriate. A rollback does not automatically reverse database migrations or external side effects.

Costs and usage

Check current Cloudflare plan limits and the pricing of every connected service before launch. Domain registration, paid mailbox hosting, third-party APIs, databases and email sending may cost extra even if static hosting is inexpensive. Set usage alerts where available and avoid assuming every feature is unlimited or free.
