# Frameworks and build settings
**Last updated:** 18 October 2026

Cloudflare supports many frameworks, but the correct deployment depends on the kind of output your framework produces. A project that builds to static files is different from one that needs server-side rendering (SSR).

## Framework families

These are examples covered by Cloudflare's framework documentation. Support and recommended deployment targets can change; use the linked official guide for your exact version and features.

| Framework / tool | Typical use | What to verify |
|---|---|---|
| Plain HTML/CSS/JS | Static files | Root/output folder; no build needed |
| Vite | Frontend build tool for many frameworks | Build command and output directory (often `npm run build`, `dist`) |
| React | UI library; often with Vite or a meta-framework | React itself is not the deployment target; identify the build tool |
| Vue / Angular / Svelte | Frontend frameworks | Preset, build output and any server-side features |
| Astro | Content sites and hybrid apps | Static output versus server adapter |
| Hugo / Jekyll / Eleventy | Static site generators | Install/build command and generated output folder |
| Docusaurus / VitePress | Documentation sites | Build command and generated static folder |
| Next.js | React full-stack framework | Use Workers guide for server-rendered Next.js; Pages is for supported static export use cases |
| Nuxt / SvelteKit / Remix / SolidStart / Qwik | Full-stack or hybrid frameworks | Use the current adapter/deployment guide and confirm SSR support |
| Hono | Lightweight web framework | Often a natural fit for Workers APIs and routes |

Cloudflare’s Pages framework guide lists many more frameworks. “Listed” does not mean every feature or every framework version behaves the same way.

## What are build settings?

- **Production branch:** the branch whose successful deployment becomes production, commonly `main`.
- **Build command:** the command that transforms source files into deployable output, commonly `npm run build` for a JavaScript project.
- **Build output directory:** the folder generated by the build that contains the files to deploy. Examples include `dist`, `build`, `public` or `out`, but never guess—check the framework's config and build log.
- **Root directory:** useful in a monorepo where the app lives in a subfolder.
- **Environment variables:** configuration values supplied at build or runtime. Public frontend variables can be included in client bundles, so they are not secrets.

## Example: a typical Vite frontend

A common setup uses:
- Build command: `npm run build`
- Output directory: `dist`

These are common defaults, not universal settings. Open `package.json` and check the scripts. Run the build locally and confirm which folder was produced before entering settings into Cloudflare.

## Example: static HTML

If your repository already contains `index.html`, `styles.css` and `script.js` and does not need compilation, do not install React or Vite just to host it. Use the root as the output directory and a no-build command if the deployment workflow requires one.

## Next.js warning

A Next.js static export is not the same as a full Next.js app with server-rendered pages, middleware or dynamic routes. Cloudflare's current documentation directs most server-rendered Next.js deployments to the Workers guide; Pages can still be used for supported static exports. Read the specific guide before migrating.

## Create a new starter

Cloudflare provides the Create Cloudflare CLI (C3). For Pages, the documented command includes the Pages platform option:

```bash
npm create cloudflare@latest -- --platform=pages
```

Without that option, the tool may create a Workers project by default. The setup prompts let you select supported framework starters. For a new Workers project, use the current Workers getting-started documentation.

## Framework deployment checklist

1. Read the official guide for the framework and version.
2. Confirm whether you need static hosting or server-side rendering.
3. Check `package.json` scripts and lockfile.
4. Run a clean install and build locally.
5. Confirm the output folder exists and contains the expected entry files.
6. Configure the matching Cloudflare preset, root, command and output folder.
7. Add runtime bindings and environment variables only when needed.
8. Test routes, API calls, redirects, image handling and error states on the deployed preview.
